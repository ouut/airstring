# ops/ — 开发侧（Muse）与部署/运维 agent 的沟通渠道

本目录是 airstring 项目开发侧与部署侧的**定版沟通账本**，仿照已验证的
协作规矩运行：任务与裁定以仓内文件为准，口头/转述不算数。

## 角色

- **开发侧（Muse）**：写任务、验收报告、给裁定。推送身份为仓主 `ouut`。
- **部署侧 agent**：在 Google Cloud / Firebase 环境执行部署与运维，
  按任务文件执行、把交付报告落仓。

## 文件布局

- `ops/tasks/OPS-<序号>-<短名>.md`：开发侧下达的任务文件，一任务一文件，
  只增不改（要改发新序号）。部署侧只执行任务文件里的步骤。
- `ops/reports/OPS-<序号>-report.md`：部署侧的交付报告，与任务同序号，
  写明每步成败、关键输出原文、失败时的完整报错。报告落仓才算交付。
- `ops/discuss.md`：日常沟通与状态同步，**只追加、不改历史**；改前先拉
  远程最新内容再合并追加（双方都写的文件不许直接覆盖）。

## 纪律

- 只部署、不改代码与规则的口径不变：任务文件没写的改动不要做；
  认为必须改时，停下、在 discuss 里写明原因与改法，等开发侧裁定。
- 费用纪律不变：Blaze 档只用免费额度，遇付费提示停下报告。
- **任何凭据、私钥、令牌不许进仓、不许写进报告**（本仓为公开仓）。
  部署所需的登录态由部署侧自己的环境解决。
- 部署侧若遇到内容被其安全检查拦截/降权：不要静默跳过，在
  `ops/discuss.md` 追加一段写明被拦对象与提示原文，等待处理。

## 接入方式（部署侧首次执行）

1. 确认自己对 `ouut/airstring` 有 push 权限（仓主会把部署侧的
   GitHub 账号加为 collaborator；无权限时先在 discuss 渠道之外
   向仓主报账号名）。
2. clone 仓后先读本文件与 `docs/deploy-task.md`（首份任务书）。
3. 在 `ops/discuss.md` 追加一段报到：账号名、环境、当前状态。
4. 此后：新任务看 `ops/tasks/`，交付写 `ops/reports/`，日常写 discuss。
