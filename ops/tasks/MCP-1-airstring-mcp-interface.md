# MCP-1 — airstring 导入／导出接口需求（开发侧交付，部署侧执行）

下发：开发侧（主线），2026-11-21。**本版按仓主 2026-11-21 裁定收窄范围，取代同日旧版**：旧版的站内 MCP 工具集方案（stats_summary／list_games／get_game／leaderboard 等 tools 与 resources）**整章作废**，不再实施。本版口径：部署侧只加**导出接口**与**导入接口**两个出入口，并按本文实现**数据包规范**；其余数据处理全部在外部（主线侧）完成。本文为需求文档，定边界、契约与验收口径；实现细节由部署侧自定，但不得突破 §1.3 冻结清单。部署侧对口径有疑问，先在 `ops/discuss.md` 留言，不要自行改口径。

## 1. 范围与边界

### 1.1 背景与已定口径（不变）

- 站点基线：WASM 版 NetHack 3.6.7（oracle 插桩版）真人对局站；Firebase 项目 `airstring-nethack`（Blaze）；账号只走 Google OAuth；全站种子锁定＋日期钉死 `1700000000`＋关 bones，wizard/explore 局不收。对局以完整按键流录制（格式见仓内 `docs/recording-format.md`），局终自动触发验真，**verdict 只归验真器**。
- 机器人局口径（规格 §11 U-3 乙案，已决）：验真通过即上榜、不分人机；来源以账号身份与元数据自明。
- 两个数据方向：airstring → 外部（人类 verified 对局供 fleck 差分消费）；外部 → airstring（IMPORT-1 式录制包导入；beam 深局残局作分叉挑战原料）。本接口只负责把这两个方向的**搬运**服务化；数据在外部如何被统计、筛选、消费，不在本规范内。

### 1.2 部署侧交付物（只有三样）

1. **导出接口**（§3）：按粗粒度条件把站内对局打成规范数据包（§2）供外部取走。
2. **导入接口**（§4）：接收外部拼好的规范数据包，按 IMPORT-1 口径服务化落库并触发验真，产出可回查的批次报告。
3. **数据包契约的实现**（§2）：导出产出的包与导入接受的包严格同构（往返恒等）。

### 1.3 不在部署范围（全部由外部／主线侧完成，部署侧不实现、不预留）

- 统计报表与聚合（全站计数、深度分布、职业×深度矩阵、增量统计等）；
- 深度／职业／标签等一切细粒度筛选与检索；
- 导入包的拼包组装与提交前预检（本地结构校验、本地验真预跑）；
- 双向对账（两系统计数与哈希比对、消费回执、索引与标签维护）；
- B 类残局在站内的呈现、审核与分叉续打产品形态（见 §4.3，仅落库打标在本范围内）；
- 任何站内页面、榜单口径与既有功能的改动。

### 1.4 冻结清单（全程适用）

录制流格式、验真触发与判定口径、verdict 写入权、既有字段语义、种子/日期锁定与关 bones 等业务规则，一概不动。新接口只是出入口：一切落库走既有 Admin SDK／验真路径，接口本身不新增任何绕过验真器的写入通道；新增字段不得复用既有字段名表达新义。费用口径：Blaze 按量、尽量只用免费额度，预见持续超额先报仓主（§6 验收 6）。

## 2. 数据包规范（核心契约）

### 2.1 包结构

tar.gz，内含：`MANIFEST.json`、`MANIFEST.md`（人读版，与 JSON 同内容）、录制文件目录（见 2.2／2.3）。包内录制与 MANIFEST 的一致性（条数、逐条 sha、字节数）在导入校验阶段**全量核对，不抽查**。

### 2.2 A 类：完整录制（导入与导出共用，与 IMPORT-1 输入包同构）

目录：`recordings/<gameId>.jsonl`（逐局一份，录制流格式见仓内 `docs/recording-format.md`，本规范不改该格式）。

`MANIFEST.json` 顶层必填：`package`（包名）、`generatedAt`、`seed`、`date`（须为 1700000000）、`options`、`count`、`recordingsBytes`，及来源三件套 `source`、`batch`、`provenance`（导入必填校验见 §4.2；导出时由站方按数据来源如实填写）。

`entries[]` 逐条必填：`gameId`、`lineage`（来源谱系 id）、`outcome`、`endLevel`、`frames`、`keysBytes`、`recordingBytes`、`framesSha256`；可选：`chain`、`segment`、`endBranch`、`endXL`、`deathCause`、`verdict`（仅供外部对账参考，导入方忽略其权威性，见 §4.2）、`reason`（入选理由）。

- **往返恒等**：导出包必须能被导入接口原样接受；导出时 `entries[].gameId` 携带站内**原始 gameId**，再导入（回本站或测试项目）凭 gameId 幂等去重，不产生新 id、不产生双份。

### 2.3 B 类：未完成残局

结构同 2.1 骨架，以 MANIFEST 字段与 A 类区分：顶层带 `status="incomplete-unverified"` 与 `source`（及 `batch`、`provenance`）；目录为 `keys/`（逐条一份 `.keys` 文件）；`entries[]` 逐条必填：`lineage`、`keys_file`（包内 keys 文件名）、`keys_bytes`、`keys_sha256`、`end_level`、`dlvl`、`xl`、`frames`、`frames_sha`。

- **keys 完整性硬约束**：keys 必须是**从开局第一键起的完整前缀流**（与录制流拼接规则一致：header 后 turn.keys＋tail.keys 的连续拼接），缺头或中间断裂的整条拒绝并在批次报告中注原因——这是残局日后被续打、按完整按键流验真转正的前提。现有 299 条残局存档即按此形态在外部整理后提交。

## 3. 导出接口

- **粒度**：只提供两种取数方式——**全量导出**，或**按时间水位增量**。至多两个粗过滤：`status`（如仅 verified）、`since`（水位）。其余筛选一律不做，由外部在包上完成。
- **水位语义（写死）**：每次导出响应返回一个不透明水位值 `watermark`，代表「截至该水位时已可导出的全部对局均已包含在本包内」。以该水位作下一次导出的 `since`，返回的恰为其后新变为可导出的对局——**不重不漏**：历次增量包的并集与同刻全量包等价，交集为空。水位的实现载体（时间戳＋gameId 序对、服务端递增序号等）由部署侧选定，但上述语义为验收口径，不得打折。
- **响应**：`{ downloadUrl（限时签名 URL，建议有效期 ≤24h）, packageSha256, count, watermark, bytes, expiresAt }`。包本体不走接口响应正文。包内只含命中 `status` 条件的对局；不做「命中但跳过」的混装。
- **超限**：命中量超过 §5 单包上限时，回 `package_too_large` 并附命中总数，服务端不自动拆包；调用方以水位分段逐段取。
- **鉴权**：单一**导出凭据**（高熵随机串，≥32 字节），只存部署侧 Secret Manager 与主线侧保险库，不入仓、不入日志。仅凭该凭据可调导出接口，不因此获得任何其他站内权限。
- **审计（最小要求）**：每次调用（含被拒）落一条记录：时间（UTC）、凭据标识、过滤条件摘要、结果计数、包 sha256、水位、状态（ok/error＋错误码）、耗时。日志不含凭据值、不含录制正文，保留期 ≥180 天。

## 4. 导入接口

### 4.1 提交方式（两案，部署侧评估后在报告中选定并说明理由）

| 案 | 形态 | 取舍点 |
|---|---|---|
| A | HTTPS 上传：外部把包体（或包引用＋sha256）直接提交到导入 endpoint | 一步到位、批次 id 即时返回；大包受 endpoint 载荷／超时上限约束，可能需分片或引用式提交 |
| B | 约定存储位置投递＋触发：外部把包放到约定桶路径并调用触发接口（只传路径＋sha256） | 大包友好、与既有 Storage 栈同体；多一步投递约定与孤儿文件清理口径 |

两案的**处理语义（§4.2）与批次报告（§4.4）完全一致**，选案只影响搬运形态。判据（按序）：单包上限（§5）内的大包是否稳定可达；与现有部署管线契合；免费额度内的常态成本。

### 4.2 处理语义（IMPORT-1 的服务化版本）

导入为异步批次制：提交只做「收包＋整包校验＋建批次」，落库与验真触发在批次执行内完成，批次 id 在提交响应中返回。

- **整包校验**（任一不过整批拒绝、不落库）：包 sha256 与申报一致；MANIFEST 可解析且必填项齐（§2）；来源三件套 `source`／`batch`／`provenance` 齐全（缺一整批拒绝）；每条录制 header 中 seed/date/options 与站方受控条件一致（date=1700000000、options 为站方默认拼装、无 bones/wizard/explore 痕迹）；条数与体积在 §5 上限内。
- **归属与落库**：A 类导入局挂官方机器人账号（IMPORT-1 已建的 `Beam Search` 或同性质账号）名下；录制落 `recordings/<bot-uid>/<gameId>.jsonl`（或现行规范路径），games 文档按客户端同款字段创建（status=pending、**不带任何 verdict 字段**、seed/date/options 与录制 header 一致），逐条写来源元数据（source、batch、MANIFEST 的 lineage）。
- **幂等**：以 gameId 为键——Storage 写用 `ifGenerationMatch=0`、Firestore 建文档前查存。已存在的 gameId 记 `duplicate`，不覆盖、不重复触发验真。同包可安全重提。
- **验真**：新落库条目逐条按现行机制触发验真器；verdict 只由验真器写。导入方不得依据包内自带的 `verdict` 字段做任何落库标注（该字段仅供外部对账参考）。
- **逐条结果**：每条为 `imported`／`duplicate`／`rejected` 三态之一，rejected 必带原因原文（如结构校验失败点、验真器原文）。整包校验失败与逐条 rejected 的区分：前者整批不落库，后者仅该条不落库、其余照常。

### 4.3 B 类处理

B 类包走同一导入接口，按 §2.3 校验（含 keys 完整性硬约束）。落库只做两件事：存档＋打标（`status="incomplete-unverified"`、来源三件套、终点摘要字段）。不建普通对局文档、不触发验真、不进榜单与统计口径。去重键＝来源谱系 id＋keys sha256，同键重入记 duplicate。**残局在站内的呈现、审核与分叉续打形态不在本规范范围**，另行议定。

### 4.4 批次报告

每批次产出一份报告（沿 IMPORT-1 报告惯例落 `ops/reports/`，且可凭批次 id 经导入接口回查）：批次 id、提交与完成时间、包 sha256、总数与三态计数、逐条结果清单（gameId 或谱系 id、状态、原因如有）、异常原文（如有）。回查与提交共用导入凭据。

### 4.5 鉴权

**导入凭据与导出凭据分开**（同 §3 的保管口径）。导入凭据只授权「调用导入接口」本身：落库一律经服务端内部的既有 Admin/验真路径完成，导入凭据**不得**具备写 verdict、改冻结字段或直写 Firestore/Storage 的能力。凭据支持新旧并行轮换，轮换与废止记入审计。

## 5. 错误与限额

错误一律回结构化错误对象（code＋message），不吞异常、不假成功。最小错误码表：

| code | 含义 | 行为 |
|---|---|---|
| `unauthorized` | 凭据缺失或无效 | 拒绝，记审计 |
| `package_format_invalid` | 包不可解析／结构不合 §2 | 整批拒绝 |
| `manifest_missing_field` | MANIFEST 必填项缺失（附字段名） | 整批拒绝 |
| `source_metadata_missing` | 来源三件套缺失 | 整批拒绝 |
| `sha_mismatch` | 包或逐条 sha 与申报／MANIFEST 不一致 | 整批拒绝（包级）／该条 rejected（条级） |
| `controlled_condition_mismatch` | 录制 header 的 seed/date/options 与站方受控条件不符 | 该条 rejected，附差异点 |
| `package_too_large` | 超 §5 上限 | 整批拒绝（导入）／附命中总数（导出） |
| `rate_limited` | 超调用频率上限 | 拒绝，不排队 |

逐条 rejected 的原因（如验真器拒绝原文）不设独立错误码，随批次报告以原文回传。

**单包上限（建议值，标注可调，最终数值见 §7 待裁）**：条数 ≤200 条、体积 ≤512MB。超限行为：导入整批拒绝、零落库；导出按 §3 回错由调用方分段。频率上限建议：导出 ≤6 次/分钟、导入同时至多 1 个未完成批次（串行化）。

## 6. 验收标准（逐条可测）

1. **往返恒等**：取站内任意 ≥10 条 verified 局经导出接口导出，在外部原样经导入接口提交回测试项目（或本站测试租户）：异站逐条 imported 后验真 verdict 与原局一致、帧哈希链 sha 逐条相等；同站重导逐条为 duplicate。
2. **幂等重入**：同一 A 类包连续提交两次，第二批逐条全为 duplicate、库内零新增、验真器零新触发。
3. **增量水位**：在两次导出之间新增若干 verified 局，第二次以第一次返回的水位增量导出：两包条目交集为空、并集与同期全量导出逐条一致（gameId 集合相等）。
4. **未验真不进榜**：导入一条将 pending 的局与一条将被 rejected 的局，站内榜单均不含之（接口不改变既有榜单口径，此条为回归项）。
5. **端到端一例**：外部经导出接口取站内最新一条 verified 深局（Dlvl≥21），在 fleck 既有差分管线中以（种子＋按键流）重放通过（逐帧哈希全等）。
6. **费用检查点**：上线后第 7 天与第 30 天各出一次用量小结（接口调用数、带宽、函数/存储用量、对应 Blaze 计费项）与免费额度对比；任一计费项出现持续增长趋势即先报仓主再继续放量。
7. **冻结清单回归**：接口上线前后各跑一次站内既有验真抽查（任选 3 条存量局重验），verdict 与帧 sha 不变；Firestore/Storage 客户端规则无放宽（规则文件 diff 为空或仅收紧）。

## 7. 待裁清单（只留接口层面，部署侧勿自行决定）

1. **接口形态**：§4.1 提交两案（HTTPS 上传 vs 投递＋触发）选定，及导出接口的承载形态，部署侧给出评估与建议、仓主定。
2. **凭据保管与轮换**：两个凭据的生成、主线侧保管方式（保险库条目归属）与轮换责任人待定；部署侧只负责 Secret Manager 侧落点。
3. **单包上限数值**：§5 建议值（200 条／512MB）是否合适——通关局录制体积显著大于普通局，可能需按体积单独放宽——待实测一批后定。
