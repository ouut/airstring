## 0. 总纲

### 0.1 定位

airstring.org 是公开可玩的 web 版 NetHack，承担两项职能，按优先级排序：

1. **收真人轨迹（当务之急）**：让真实玩家在受控、可复现的环境里对局，产出的（种子＋按键流）经自动验真后成为 fleck 的差分资产。首要采购目标是通关局——fleck 阶段 20 关期缺的正是全程通关轨迹。
2. **fleck 的对外门面**：站点即 fleck 项目的公开入口；二期把游戏内核从 C 版换成 fleck（Rust/Flecs ECS 版），三期开放开发者扩展。前端、账号、榜单、存档在换芯时整体平移，不推倒重来。

### 0.2 基座路线（定案，不再议）

- 一期基座＝**oracle 版**：fleck 仓 `oracle/` 树（NetHack 3.6.7＋fleck.c 插桩＋求值顺序定序修复）构建的 C 二进制。内容完整、13 职业齐备、今天可玩。
- 服务器上运行的二进制与验真用的二进制**必须是同一构建产物**（同一 sha），轨迹零转换：玩家按键流即回放文件，回放即验真。
- fleck 版何时换芯由 fleck 侧完成度决定（见 §10 M2 的前置条件），不在本规格内排期。

### 0.3 非目标（一期明确不做）

- **图块（tiles）渲染：已议定不做（2026-11-19）**，只做高质量字符终端。理由写死在此：本站核心用户是老玩家，老玩家主流偏好字符终端——读屏快、符号无歧义；图块辨认有歧义、读屏慢，在老玩家群里普遍减分。且图块须按 glyph 渲染，本站记录与显示的地基是纯 pty 字符流，字符流到图块的映射有损，做图块是独立的大工程，对 §3 轨迹采购目标无贡献。结论：v1 不做；将来若做，也只是可选显示层，不动会话与记录核心。
- 不做观战（列 v1.1 候选，未决）。
- 不做站内支付、广告、社交关系链（好友/私信）。
- 不与 NAO / hardfought 争「主服务器」地位；定位见 §9。

### 0.4 术语

- **局**：一局完整对局，从开局进程启动到进程退出（通关/死亡/退出/逃出）。
- **按键流**：pty 网关写入游戏进程 stdin 的完整字节序列，与 fleck 回放格式同构。
- **验真**：在独立 oracle 实例上以（种子＋按键流）从头回放，比对帧导出与 RNG 审计是否与局内实时导出逐字节一致。
- **目标局**：为 fleck 特定缺口定向征集的对局（通关、某职业 Quest、某长尾条目），清单见 §3。

## 1. 系统总览

站点由五部分组成，边界如下：

| 组件 | 职责 | 备注 |
| --- | --- | --- |
| Web 前端 | 落地页、账号、开局表单、终端、回放器、排行榜、录像库 | 静态资源＋少量动态页 |
| 会话服务 | 账号会话、开局编排、pty 网关、断线重连、存档管理 | 每局一个游戏进程 |
| 游戏进程 | oracle 二进制，受控 env 启动 | 进程隔离见 §6 |
| 收割管线 | 局终归档、元数据落库、验真任务投递 | 与站点同步部分只做落盘 |
| 验真 worker | 异步回放验真、回写状态、打消费标签 | 可跑在证据级机器（friends-vm1 / ARM 机），与站点解耦 |

数据流主线：玩家浏览器 ⇄ 会话服务（pty）⇄ 游戏进程；按键流与帧/审计导出旁路落盘；局终触发归档 → 验真 → 入库 → fleck 侧按标签取用。

## 2. 核心机制

### 2.1 种子分配

全站每一局的种子一律由服务器记录并写入游戏进程 env（`FLECK_SEED`），玩家不可指定进程实际使用的种子数值之外的任何 RNG 输入。对局之间唯一的区别是种子来源（详见 §2.5）：

- **指定种子**：玩家自选输入任意种子值（64 位空间内），或从种子榜/情报板选定，服务器原样采用并记录；种子 1–5000 有探针情报（§4.10）。每日种子与目标局是指定种子的特例：每日种子由 UTC 日期按固定公式派生、全站当日同一种子，供每日种子榜与玩家间可比对局；目标局由 fleck 侧指定种子征集（§3.3）。
- **随机种子**：服务器以系统熵从 64 位空间随机抽取并记录，玩家开局前不可见、局终后可查看。
- **接力/分叉**：子局继承父局种子（见 §4.11）。

### 2.2 日期钉死

- 全站每局 `FLECK_DATE` 钉死为与 fleck 护照一致的固定值，游戏内日期、月相恒定。
- 这是可复现的前提条件，不是可选项；玩家侧须明示：在开局页与 FAQ 写明「为保证成绩可验真，游戏内日期固定，月相恒定，与真实日期无关」。

### 2.3 运行口径（与护照一致）

游戏进程启动 env 固定如下，全站任何对局不得增减：

- `TZ=UTC`
- `FLECK_DATE`＝固定值（见 §2.2）
- `FLECK_SEED`＝本局种子（见 §2.1）
- `FLECK_EXPORT`、`FLECK_RNGLOG` 指向本局归档目录（实时导出帧与 RNG 审计）
- `NETHACKOPTIONS` 由服务器按开局表单拼装（name/role/race/gender/align 来自表单，其余选项用站内固定集，玩家不可注入任意选项串）

启动前清空本局 nethackdir 的 save/bones/record 残留；二进制路径与 sha 在站点配置中钉死，升级二进制须走 §6.4 的变更流程。

### 2.4 按键流记录

- 记录点在 pty 网关：凡写入游戏进程 stdin 的字节，按序、无损、带局 id 落盘为本局按键流文件。玩家终端尺寸协商、窗口调整等控制序列不进按键流（只记实际送达游戏的输入字节）。
- 按键流文件即 fleck 回放格式，验真与 fleck 侧消费时不做任何转码。
- 记录完整性要求：进程异常退出、玩家断线、服务器重启三种情况下，已落盘部分不得损坏；采用追加写＋定期 fsync，局终做最终封口（见 friend2 分包，§8）。
- 实时帧/审计导出（§2.3）与按键流互为交叉核对：验真以回放产物为准，实时导出为比对基准。

### 2.5 全站受控条件与种子来源

本站没有模式之分：**全站每一局都在同一套受控条件下进行**，条件与 fleck 的验真口径完全一致——

- 种子必记录（`FLECK_SEED`，见 §2.1）；
- 游戏内日期钉死（`FLECK_DATE`，见 §2.2）；
- **bones 关闭**：每局独立 nethackdir，不投放 bones 文件；
- **wizard / explore 不收录**：全站不开放，启动参数与账号权限双重拦截，`-D`/`-X` 一律拒绝；
- 选项受控（§2.3）；
- 存档账号绑定（§2.6）。

由此全站对局皆可回放验真、皆进收割管线（§5），不存在不受控、不可验真的对局。对局之间唯一的区别是**种子来源**：

| 种子来源 | 说明 |
| --- | --- |
| 指定种子 | 玩家自选输入，或从种子榜/情报板选定（§4.10）；种子 1–5000 有探针情报 |
| 随机种子 | 系统从 64 位空间随机抽取并记录，玩家开局不知、局终可查看 |
| 每日种子 | 指定种子的特例：按 UTC 日期派生，全站当日同一种子（§2.1） |
| 目标局 | 指定种子的特例：fleck 侧为缺口定向征集的种子（§3.3） |
| 接力/分叉 | 继承父局种子（§4.11） |

关 bones 的理由只写一遍：bones 文件会改变关卡内容，加载过 bones 的局在干净环境回放必然分歧、整局作废；本站全部价值在可复现，故全站关。

### 2.6 存档与会话持久

- 存档即游戏进程的原生 save 文件，由会话服务按账号托管，存放在该账号的专属目录；玩家不直接接触文件。
- **断线重连**：玩家浏览器断开时，会话服务保持游戏进程与 pty 存活（dgamelaunch 式会话持久），玩家重新登录后 reattach 回同一局，按键流连续不断档。
- 一账号至多一个活跃局；已有活跃局时开新局须先结束或放弃旧局（放弃＝进程终止、该局按未完成归档、不验真不上榜）。
- 闲置局：活跃局连续 72 小时无输入，会话服务向进程发送保存退出，存档保留，玩家回来可续；不自动删除存档。
- 服务器维护重启前须优雅处理全部活跃局（逐个保存退出），重启后玩家凭存档续玩；按键流按局跨重启拼接，封口时合并为一份。

## 3. 数据需求与目标局清单

站点一期的成败按本清单验收，不按注册量或总对局数。总量约 25 条目标局，估算 30–60 高手人时。

### 3.1 通关局（最高优先级）

- 需求：**1–3 条**完整通关局（任意职业、任意种子，验真通过）。
- 用途：关 fleck 阶段 20 主链（祈唤→Sanctum→夺 Amulet→五元素位面→升天全程差分）。
- 备注：第一条通关局即达关期条件；第 2–3 条为备份与路径多样性（不同职业优先，与 §3.2 可重叠计算）。

### 3.2 Quest 职业局

- 需求：Valkyrie 之外**其余 12 职业各 1 条**任务线局（进入本职业 Quest、打穿五层、击杀宿敌、取得任务物品并返回主线即算达标，不要求通关）。
- 用途：fleck Quest Q2 起逐职业差分（Q1 仅 Valkyrie 已完成）。
- 备注：若某职业玩家顺势通关，该局同时计入 §3.1 与本节。

### 3.3 长尾定向局

- 需求：约 **10 条**短局，按 fleck 长尾台账逐项征集（示例条目：LT-3 回变、LT-4 抢商店、溺水链、宝座、Excalibur 蘸水链、被吞战斗、传送门穿越；以台账现行版本为准，清单由 friend1 维护，见 §8）。
- 形式：指定种子＋指定目标（如「seed N，Tourist，打到 X 触发 Y」），站点以目标局形式发布，玩家认领。

### 3.4 自由局

非目标局的对局照常收、照常验真入库，标签为 `free`。自由局是目标局的蓄水池（玩家先自由玩、熟悉站点后认领目标局），也是长尾的意外覆盖来源，不得因未标注而丢弃。

## 4. 功能规格（v1）

### 4.1 账号

- 登录**只走 OAuth**：Google 账号为主、GitHub 为备选。**明确不做邮箱＋密码注册，本站不存任何密码**、不接触玩家的账号凭据，凭据安全由 OAuth 提供方承担。
- 首次 OAuth 登录即自动建号；站内用户名取自 OAuth 账号的登录名/显示名（冲突时加后缀消歧），玩家可在设置中改名一次；用户名规则与公开服务器惯例一致（字母数字下划线，长度 3–16）。
- 登录态：服务端会话 cookie（HttpOnly、Secure、SameSite=Lax）。
- 登录用途**仅为身份归属**：云存档归属（§2.6）、成绩上榜与录像归属（§4.6、§4.7）、接力谱系的作者链（§4.11）。不登录可浏览落地页、排行榜、情报板与公开录像库；开局须先登录（对局须归属到账号才能存档与入库）。

### 4.2 网页终端

- 前端采用 xterm.js 类终端组件，经 WebSocket 与会话服务 pty 相连；桌面浏览器键盘完整映射（含 Esc、方向键、功能键组合）；移动端见本节末「移动端」小节。
- 字体与配色：等宽字体（站内托管，不依赖外部 CDN）、深色底、NetHack 传统 16 色映射校准；终端尺寸固定 80×24 逻辑网格，浏览器窗口缩放只改字号不改网格。
- 输入纪律：浏览器快捷键冲突（如 Ctrl+W）在开局前以提示页明示；终端获得焦点时拦截游戏所需按键。

**移动端（拍板要做，2026-11-19；分两步，排期见 §10）**：

口径先行：会话与存档都在服务器端（§2.6），同一账号换设备 reattach 同一局本就是架构自带属性，跨设备续玩不需要额外机制；移动端纯粹是输入/显示层，不动游戏与记录核心。

**输入方案：上下文操作栏（v0.5 定案，取代原全量虚拟键条方案）**。设计依据：NetHack 是回合制＋模态输入，游戏在任一时刻只等待一类输入（主命令／方向／物品选择／是非确认／菜单／文本输入），每一步真正可选项有限，几十个命令键不需要、也不应该同时呈现。官方 NetHack 5.0 仍是全键位模型（界面侧仅新增教程、自动开门、危险动作确认与状态颜色），上下文操作栏是本站前端自己的设计；第三方 5.0 前端（如 macOS 的 Atlas）已有同类「按脚下与周边地物推荐动作＋可搜索完整命令列表」实现，可作参照。三层结构：

- **移动层**：点按相邻格移动/攻击、点按远格按 travel 语义寻路过去、点按对象查看；常驻小方向区、等待与搜索。
- **上下文操作条**：按当前提示状态与环境生成可点选项——主命令态按脚下/相邻地物与相邻怪物生成（拾取、上下楼、开/关门、搜掠容器、交谈等）；方向提示态给 8 方向＋自身＋取消；物品选择态直接渲染游戏给出的可选物品列表供点选；是非确认态给按钮。
- **兜底层**：「全部命令」可搜索面板覆盖全部命令与扩展命令（含低频与边缘尝试，如踢墙）；只有刻字、许愿、命名等文本输入场景才弹出系统键盘。桌面端保留完整物理键盘映射，老玩家习惯不受影响。

实现纪律：提示状态由前端解析终端输出流判定（必要时由会话服务旁路提供）；点按一律翻译成原按键序列发送，录制仍是按键流，§5 验真与收割管线不受影响。操作条只列「当前情境下合理」的动作，不承诺成功，不改变游戏语义。

- **M0 基础版**：响应式布局（终端区按屏幕宽度缩放字号，逻辑网格仍 80×24）＋移动层＋上下文操作条（覆盖主命令、方向、物品选择、是非四态）＋全部命令面板，保证手机上全部输入可达、「能玩、能续玩」——打开就能玩、随时随地接着玩，把游玩门槛压到最低。
- **M1 补全触控体验**（公开 beta 前置，见 §10 M1 过线标准）：物品反选（点背包物品、按其类别列出可用动作，如药水→喝/蘸/扔）、点按查看补全、长按重复与计数输入、操作条布局与误触间距按触控实测调校。

### 4.3 开局

- 开局表单：种子来源二选一（指定种子——自选输入或从种子榜/情报板选定；随机种子——系统抽取，开局不知、局终可查看）→ 职业、种族、性别、阵营（按 3.6.7 合法组合联动过滤，非法组合不可选）。每日种子入口是指定种子的一种快捷预填。
- 目标局认领入口与开局表单打通：从目标局清单点「认领」即预填种子与角色，局终自动与该目标局条目关联待核。

### 4.4 云存档续玩

- 账号首页列出本账号活跃局与存档（角色、种子来源与种子、开始时间、最后活动时间），点「继续」即 reattach 或由存档恢复。
- 行为细则见 §2.6；前端不提供删除存档以外的进程管理（放弃对局须二次确认）。

### 4.5 录像回放器

- 数据源＝（种子＋按键流）：服务端按需在 oracle 实例上重放，导出全程帧序列后下发前端渲染；已验真的局可预生成并缓存帧序列，避免重复重放。
- 渲染：按帧绘制 80×24 字符网格（含颜色与粗体属性），不依赖终端组件，与游玩终端视觉一致。
- 控件：播放/暂停、逐帧前进/后退、变速（0.5/1/2/4/8 倍）、进度条拖动（帧序列整段下发后本地定位，拖动零延迟）、帧号/回合数（moves）显示、下载按键流与元数据（JSON）。
- 播放语义：帧序列以游戏帧为单位，不做插值；暂停即停在当前帧。

### 4.6 验真排行榜

- 准入：验真通过、局已封口（全站对局同为受控条件，入库不按任何模式过滤）。未验真或验真失败的成绩不进任何榜单（含玩家自己的历史页须标注状态，见 §4.7）。
- 榜单三类：总榜（分数降序，同分以回合数少者优先）、每日种子榜（按日切分，当日种子内排名）、职业榜（每职业取个人最佳一条）。
- 成绩字段：用户名、分数、职业/种族、结果（ascended/died/quit/escaped）、最深层、回合数、对局时长、种子、日期、录像链接。
- 榜单只读公开，无需登录可看；录像随成绩公开（玩家可在账号设置中把本人录像设为不公开，成绩仍上榜、录像链接隐藏）。

### 4.7 个人历史与公开录像库

- 个人历史：本人全部对局，含状态（进行中/待验真/验真通过/验真失败/未完成）与录像入口。
- 公开录像库：全部验真通过且未设不公开的录像，可按职业、结果、种子、日期筛选；目标局录像单独置顶区。

### 4.8 落地页

双层叙事，文案以事实为准、不写营销辞令：

- 上层：现在可玩的忠实 NetHack 3.6.7（原版规则、种子对局、可验真排行榜），直接给「开始玩」入口。
- 下层：本站同时是一个开源复刻项目（fleck，Rust＋Flecs ECS）的数据来源——玩家每局验真对局都成为复刻版的差分测试资产；ECS 版与开发者计划在路上，链接到 fleck 仓与 §7 的源码页。

### 4.9 FAQ

至少覆盖：为什么游戏内日期固定（§2.2）、验真原理（种子＋按键流重放、服务器跑的与验真的是同一二进制）、种子来源的区别（指定/随机，每日种子与目标局是指定种子的特例）、为什么本站没有 bones、存档与断线续玩规则、成绩为什么要等验真才上榜、源码与许可证在哪（§7）、机器人/脚本代打的现行口径（验真即上榜、不分人机，榜单只证明成绩为真，见 §11 U-3 已决）。

### 4.10 种子情报板与种子榜

- **种子情报板**：展示主线探针实测的种子情报（现行覆盖为种子 1–5000：地形评分、Minetown 变体、分支与关键地形分布等，以探针现行产出为准，随探针扩面更新）。页面必须明示覆盖范围与未覆盖项：**怪物密度、早期装备未测**；情报只说明「这颗种子的地形与城镇是什么样」，不承诺难度与掉落，不许把情报说过头。
- **剧透隔离**：情报板是独立页面，与盲打开局入口分离——开局表单默认不展示任何情报，玩家自愿点入才看。看过情报再打的局与盲打局数据上同等有效（验真只依赖种子＋按键流，与玩家是否知情无关），照常入库与上榜。
- **种子榜**：同一颗种子之下的横向排名，排序键依次为：是否通关、最深到达层、回合数（少者优先）。任一种子有 ≥1 条验真通过的对局即自动成榜；§4.6 的每日种子榜是种子榜在每日种子上的特例，口径一致。种子榜页面只列成绩，该种子的情报经链接自愿点入（不把剧透内容直接铺在榜页）。

### 4.11 接力与分叉（M1）

- **机制**：任一已封口的对局（父局），玩家可申请从其第 N 回合分叉接力：服务器以（父局种子＋父局按键流的前 N 回合部分）在 oracle 上回放到该回合、还原游戏状态，接力者从该状态续打成一局新局（子局）。分叉点可以是父局的任意回合、可以在父局进程中的任何位置——不要求父局作者打到某处「存档点」，回放还原只依赖种子＋按键流。
- **轨迹完整性**：子局的完整按键流＝父局按键流前缀＋接力者新打出的按键流，拼接后仍是一条从开局起可整体回放的轨迹，按 §5.2 同口径验真；验真通过即照常入库、打消费标签（§5.3）。
- **谱系元数据**：子局元数据（§5.1）在既有字段之外增记：父局 id、分叉回合、作者链（历代接力者的账号序列）。多代接力形成谱系树，录像页展示谱系与各代作者。
- **榜单口径**：接力局单独分类成榜（接力榜，按谱系展示），**不与个人单打成绩混排**；§4.6 三类榜只收全程由一人打出的单打局。
- **采购意义**：深层局的作者死亡后，其他高手可从死亡前的回合分叉续打救援，拼接轨迹照样构成一条可整体验真的完整轨迹——「一条命打到底」的通关采购由此放宽为「多人接力打到底」同样成立，直接服务 §3.1；Quest 与长尾目标局同理可接力。

## 5. 收割管线

### 5.1 局终事件与归档

游戏进程退出即触发局终处理（同步部分只落盘，不做重放）：

- 归档包（一局一份，目录名＝局 id）：按键流文件、实时帧导出、实时 RNG 审计、元数据 JSON、进程退出码与 stderr 尾部。
- 元数据字段：局 id、账号、种子与种子来源类型、FLECK_DATE 值、二进制 sha、职业/种族/性别/阵营、开局与局终时间、对局时长、结果（ascended/died/quit/escaped/未完成）、分数、最深层、回合数、认领的目标局 id（无则空）、接力谱系（父局 id、分叉回合、作者链，单打局为空，见 §4.11）。
- 结果字段以帧导出末帧为准自动判定，判定不了的标 `unknown` 并保留归档待人工看。

### 5.2 验真 worker

- 异步执行，不阻塞站点：从待验真队列取归档包，在独立 oracle 实例（干净 nethackdir、护照口径 env）以（种子＋按键流）从头回放，产出回放帧/审计，与归档内实时导出逐字节比对。
- 全等 → 状态 `verified`，进排行榜与入库索引；任一分歧 → 状态 `failed`，保留双方产物与首个分歧位置（帧号/审计行号）供排查，不自动重试超过 1 次。
- worker 可跑在证据级机器上（friends-vm1、ARM 机均已过 G1/G2 准入），与站点之间只传归档包与状态回写；worker 用的二进制 sha 必须与站内运行 sha 一致，不一致拒绝执行并报警。

### 5.3 入库索引与 fleck 侧消费

- 验真通过即入轨迹库索引（数据库一行＋归档包路径），打消费标签：
  - `stage20-ascension`：完整通关局；
  - `quest-<role>`：含某职业完整 Quest 线的局（role 用小写英文职业名）；
  - `longtail-<id>`：命中长尾台账条目的局（id 以台账编号为准）；
  - `stage19-deep`：到达 Valley/Gehennom 深度的局（阶段 19 备用）；
  - `free`：以上皆非。
- 标签由归档元数据＋末帧信息自动初打，目标局认领关联的以认领关系为准；标签可多值（一局可同时是通关局与某职业 Quest 局）。
- fleck 侧消费方式不变：按标签取（种子＋按键流），在 fleck 既有差分管线中作 slice 使用；本站不感知 fleck 侧的验收结论，只接收可选的消费回执（已消费/验收通过）回写索引，便于清单销账（§3）。

### 5.4 保留策略

- 验真通过的归档包永久保留。
- 验真失败的保留 90 天供排查，期满只留元数据与分歧摘要。
- 未完成局（放弃/闲置终止）保留 30 天后只留元数据。

## 6. 部署与运维

### 6.1 托管（U-1 暂定已决，2026-11-19：Firebase 免费栈，随 WASM 路线）

**预定形态（WASM 路线，见 §10 M2 与 §11 U-1）**：游戏编译为 WASM 在玩家浏览器内运行，服务端无常驻游戏进程，全部组件落 Google Firebase/GCP 免费栈：

- **Firebase Hosting**：前端＋wasm 产物＋游戏数据文件分发；airstring.org 自定义域名与 SSL 免费（免费额度：存储 10 GB、流量 360 MB/日，2026-11-19 查证）。
- **Firebase Authentication**：Google 登录（与 §4.1 的 OAuth-only 口径原生吻合），免费额度 5 万月活。
- **Firestore**：账号、榜单、局元数据与索引（免费额度：1 GiB、5 万读/日、2 万写/日；写入须按局终汇总与分块上传设计，不得逐回合写库）。
- **Cloud Storage**：按键流、存档与归档包（均为 KB 级文件）。
- **Cloud Run**：验真 worker 与接力分叉回放（无头运行同一 wasm 产物；免费额度 18 万 vCPU 秒/月＋200 万请求/月，量级可免费验数千局/月）。
- **计费形态**：用 Blaze（按量）档——Cloud Storage 与 Cloud Run 只对 Blaze 开放，Blaze 保留全部免费额度、超额才计费；挂预算告警封顶。本站量级预期月费 **$0**；唯一现实超额项是招募爆量日的 Hosting 带宽（超额 $0.15/GB，一千新访客量级约几毛钱），前端须做 wasm 包缓存以压重复下载。

**过渡形态（备选，默认不启用）**：若 WASM 路线评估不过、被迫先行服务端模式，游戏会话层（常驻进程＋pty，免费栈无处安放）临时落一台**独立公网 VPS**（2 vCPU / 4 GB 内存 / 40 GB 磁盘起步；明确不用 tailnet 内的 friends-vm、friends-vm1、ARM 机——那些是内网协作与证据机器，不对公网暴露）；账号、榜单、归档等其余组件可直接先落 Firebase。切 WASM 后 VPS 退役。域名 airstring.org：HTTPS 全站强制，WebSocket（过渡形态）走 wss。**2026-11-19 用户已拍板 M0 走 WASM 一步到位，本过渡形态不启用、仅留作备选。**

### 6.2 进程隔离

（本节适用于过渡形态的服务端游戏进程与预定形态的 Cloud Run 验真 worker；WASM 形态下玩家侧游戏在各自浏览器内运行，无跨玩家隔离面。）

- 每局游戏进程独立 unix 用户或独立容器运行，工作目录为该局专属沙箱（nethackdir），进程间不可互访。
- 资源限额：单进程 CPU 与内存设 rlimit（或 cgroup 等价物），单账号并发进程数＝活跃局上限（§2.6）。
- 游戏二进制与系统目录只读挂载/只读权限；存档目录按账号隔离。

### 6.3 备份

- 每日备份：账号库、存档、归档包与索引库，异地保存一份（可回主线 VM），保留 30 天日备＋永久保留验真通过的归档包（其本身即资产，不随日备滚动删除）。

### 6.4 变更流程

- 二进制升级（oracle 树有新构建）须：新构建先过 G1/G2 护照 → 站内灰度（仅内测账号）跑通一局并验真 → 全量切换并在站点 changelog 记录新旧 sha 与切换时间。切换前存档与新二进制的兼容性须实测（旧存档在新二进制上加载一局走通）。

4. 该局入轨迹库索引并打上正确标签；
5. fleck 侧以该局（种子＋按键流）完成一次差分消费全程（取用→回放→比对流程走通，结论记录在案）。
6. 移动端基础版达标：手机浏览器经响应式布局＋上下文操作栏（§4.2）可开局并完成一局对局所需的全部输入（罕见命令经全部命令面板可达、文本输入可弹键盘）；同一账号在手机与桌面之间跨设备续玩同一局走通（§2.6）。
